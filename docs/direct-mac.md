# Direct Mac / Linux AD connection

Settings supports a direct LDAPS connector running in the local backend. This mode has no Windows Worker dependency. Save the domain, AD user principal name and password under Direct Mac Connection; subsequent directory requests bind automatically. Passwords are encrypted with the application's existing Fernet secret store and never returned by the settings API or included in audit details. Keep JWT_SECRET stable and protect its .env file and database backups.

TLS uses certificate and hostname validation on port 636. Supply the corporate root/intermediate CA certificate in PEM format. Alternatively, inspect a saved DC's certificate without sending credentials, verify its SHA-256 fingerprint through a trusted company source, then explicitly approve that certificate. Pinned connections verify the exact certificate, DNS SAN and validity dates before binding. A changed or expired certificate stops the connection before credentials are transmitted. A pin approves only that DC; a trusted CA enables failover to other enabled DCs. A single DC provides the domain-wide directory; no per-DC pairing is necessary. Automatic LDAP referrals are disabled.

The account needs normal AD read access and delegated rights for requested writes. Wrong credentials are tried once and further attempts are suppressed until settings are re-saved. Search results use LDAP paging; an error on any page fails the query instead of reporting incomplete data as a successful directory. Network failures are briefly cached to keep initial dashboard requests from repeating failed binds. Disabled or out-of-domain configured hosts are excluded from direct connections.

Supported reads: users and user details, direct group membership, groups, computers, OUs, domain/forest identity and FSMO ownership, DC/site/subnet inventory, trusts, password policies and GPO inventory. Last logon uses replicated lastLogonTimestamp and is approximate, not an immediate per-DC lastLogon measurement. Computer/DC IP fields are not synthesized; configured IPs remain in Settings. OU accidental-deletion protection, recycle-bin and replication status are reported as unknown/unavailable.

Supported writes: edit user attributes, unlock, enable/disable users and computers, reset user passwords, move/delete directory objects, create groups and change direct group membership. Membership inventory excludes primary-group membership. Password reset reports a partial outcome explicitly if setting change-at-next-logon fails after the password was changed. LDAP writes use the existing RBAC and audit routes. No production directory writes are performed during installation/testing.

Not implemented: user creation, protected OU creation, recursive OU deletion, computer account reset, GPO management/SYSVOL reports, replication health, deleted-object inventory/restore, and forest-wide searches across other domains. Unsupported routes return HTTP 501; the UI marks unavailable modules and disables relevant actions. Direct mode does not provide full Windows RSAT parity.

Docker Compose uses a configurable RSAT_DOCKER_SUBNET (default 192.168.247.0/24) to avoid overlap with corporate 172.x networks. Recreate the Compose network after changing its subnet, retaining the PostgreSQL volume. Docker's other bridge/VM routes can still overlap corporate ranges and must be checked if particular DCs cannot be reached; choosing a reachable preferred DC is sufficient for domain-wide directory access.

Validation: backend pytest (including LDAP mock reads/writes, paging, injection escaping, invalid-password suppression, certificate pin checks and routing), frontend production build, authenticated local API smoke checks, and a live TLS handshake without AD credentials. Real AD bind and directory responses must be verified after the operator supplies their credential and certificate trust in the local panel.

The native Users UI now requests 15 records at a time using signed, expiring LDAP paging cursors tied to the search, DC and connection configuration. Previously loaded pages are retained for backward navigation. Search uses username/name/email prefixes to avoid expensive leading-wildcard scans on large domains. Overview does not infer domain-wide user or lockout totals from a single page. Groups, computers and OUs retain complete API results and render 100 rows per UI page. Loading and read failures remain visible. The web proxy permits longer legacy full-list reads, but the normal Users UI does not require them.

## Direct DNS and DHCP service management

DNS inventory uses validated LDAPS. Direct mode creates/deletes A, AAAA, CNAME, PTR, NS, MX, SRV and TXT records through Samba DNS RPC, with required Kerberos authentication and RPC packet privacy. The domain account comes from encrypted Settings storage; a five-minute ticket is obtained in a private temporary credential cache and removed after the operation. Passwords are passed only to kinit through stdin, not arguments or protocol helper JSON. DNS RPC uses the endpoint mapper and dynamic service ports; it does not require WinRM or a Windows Worker. Zone creation/deletion remain available only in optional WinRM mode. The read-only connection probe confirms DNS RPC connectivity, not permission to perform every write. DNS record ACLs remain enforced by the server.

DHCP uses Impacket MS-DHCPM RPC with Kerberos and packet privacy. Select the actual DHCP service host from the authorized servers discovered in AD; a Domain Controller without DHCP will have no DHCP RPC endpoint. Scopes, leases and reservations are fully enumerated with resume handles. Supported changes: create/delete IPv4 scopes, activate/deactivate scopes, and create/delete MAC reservations. These use the existing application roles plus actual Windows DHCP permissions. Scope creation initially creates an inactive scope, sets its range and lease duration, and then activates it if requested. Partial failures are explicit and never silently rolled back or retried. DHCP utilization counters are currently unavailable and displayed as a dash. Exclusions, options beyond initial lease duration, DHCPv6, failover configuration and lease deletion/editing are not implemented.

The isolated tests validate NDR serialization for scope and reservation writes, denied permissions and partial failures. Installation checks do not modify production records, scopes or reservations. SSH configuration is independent of AD/DNS/DHCP. The DNS helper retries only an initial RPC bind rejected with STATUS_INVALID_PARAMETER, before any operation has been sent. DNS updates themselves are sent once and are never automatically retried.

DNS record editing replaces the selected original RDATA with its new value and TTL in a single DnssrvUpdateRecord2 call. Zone/name/type remain fixed during editing; other records at the same name are preserved. MX values use `priority target`; SRV uses `priority weight port target`; TXT uses quoted text segments, preserving their boundaries for exact deletion/update matching. SOA and unknown types remain read-only. Records have their own scroll area, sticky header/pagination and total count. Edit/delete controls remain visible above the records.

## SSH switches

Add each destination and account in SSH. Inspect its host key, verify its fingerprint through a trusted source, and approve it before connecting. Passwords are encrypted in the backend; destination and fingerprint checks happen before authentication. Account-only updates preserve encrypted passwords and approved host keys. Changing the destination requires re-entering its password and re-verifying its host key. The LOGIN column distinguishes approved host keys from ready credentials; Connect opens the credential form when needed. The backend refuses a connection ticket with an empty username. Interactive sessions use a short-lived, single-use WebSocket ticket and a PTY. Terminal text is not written to audit logs.
